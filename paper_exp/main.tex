\title{Research Intelligence Engine: Architecture and Empirical Characterization of a Desktop Multi-Source Scholarly Retrieval and LLM-Annotation Pipeline}

\author{\IEEEauthorblockN{Suryavansh Jaggi}
\IEEEauthorblockA{IILM University, Greater Noida\\
suryavansh.jaggi.cs27@iilm.edu}}

\maketitle

\begin{abstract}
Open scholarly-metadata services make it practical to build local literature tools that query many providers at once, yet little is known about how such clients behave when providers are slow, fail, or disagree about metadata. We characterize the Research Intelligence Engine (RIE), an open-source Electron/PostgreSQL desktop application that fans a query out to six providers, normalizes and deduplicates the results, stores them, and sends abstracts to a hosted LLM. Evidence is kept in separate classes. Controlled experiments run RIE's unmodified modules against a deterministic emulator of the upstream APIs (the live APIs were unreachable from our cloud sandbox) and a real PostgreSQL server. Search latency tracks the slowest adapter within 11\,ms, but provider throttles impose a 350\,ms floor and up to $\approx$2.6\,s of delay on back-to-back searches, a hung provider blocks all results until its 15--30\,s timeout, and arXiv failures are reported as empty successes. The deduplicator is order dependent (1\,000 or 2\,000 output records for identical inputs) and merges DOI-less records only when metadata strings match up to letter case. The AI client is serial, spaced by 2\,s, retries only HTTP~429, and sends the literal text ``null'' for missing abstracts. A separate, single, user-recorded live session on a Windows desktop (query ``transformers'': four providers returned two papers each, Semantic Scholar returned HTTP~429, and eight papers were analyzed and saved in 27\,s) is consistent with these findings but is not a benchmark. Contributions are engineering and empirical; no retrieval-quality or LLM-quality claims are made.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Researchers who need to survey a topic increasingly query open scholarly-metadata services directly rather than a single curated index: OpenAlex~\cite{priem2022openalex}, Semantic Scholar~\cite{lo2020s2orc,kinney2023semantic}, Crossref~\cite{hendricks2020crossref}, Europe~PMC~\cite{ferguson2021europepmc}, PubMed through the NCBI E-utilities~\cite{sayers2022eutilities}, and arXiv~\cite{arxivapi}. Coverage, metadata completeness and citation counts differ between such sources~\cite{visser2021large,gusenbauer2020which,alperin2024analysis}, so a tool that queries several of them must (i)~reconcile heterogeneous schemas, (ii)~tolerate partial failure and provider rate limits, and (iii)~remove duplicates that arise because the same work is indexed by several providers under different identifiers. Separately, large language models (LLMs) are now used to summarize individual papers, with a well-documented risk of unsupported output~\cite{ji2023survey,tang2025llmreview}.

The Research Intelligence Engine (\RIE) is an open-source desktop application (Electron~$+$ PostgreSQL) that packages these functions into one workflow: concurrent retrieval from six providers, normalization into a canonical record, in-memory deduplication, relational persistence with PDF acquisition, abstract-level LLM analysis through a hosted inference API, and a Markdown/\LaTeX{} editor. To our knowledge, version~1.0.0 of the code base has no published evaluation, and its README describes a narrower and partly different system than the code implements (\cref{sec:impl}).

This paper reports what can be established about \RIE{} from its source code and from controlled experiments on its actual modules. We pose four research questions.
\begin{itemize}
\item[\textbf{RQ1}] How does the implemented fan-out strategy determine end-to-end search latency and failure containment?
\item[\textbf{RQ2}] How reliably does the three-key deduplication resolve cross-provider duplicates, and which metadata disagreements defeat it?
\item[\textbf{RQ3}] What do the local components (normalization, persistence, library indexing) cost, and how do they scale?
\item[\textbf{RQ4}] How does the AI-analysis client schedule requests, recover from errors, and construct its prompt?
\end{itemize}

\textbf{Scope and evidence classes.} The cloud sandbox in which the experiments were run blocks outbound connections to the scholarly APIs and to the LLM endpoint. The repository's real source adapters, normalizers, deduplicator, orchestrator, database layer, and AI client were therefore executed unmodified against a deterministic \emph{emulator} of the upstream HTTP interfaces (with injected latency and faults) and a real local PostgreSQL~16 server; these results are labelled \textbf{[S]} (simulated upstreams) and are reproducible with the released scripts. In addition, the author recorded one \emph{live} session of the Windows desktop application from its in-app logs; these observations are labelled \textbf{[L]}, were not independently reproduced, and are reported separately and never mixed with [S] results (\cref{sec:method}, \cref{tab:evidence}). We did \emph{not} measure real provider latency distributions, retrieval effectiveness (precision/recall/nDCG), real cross-provider overlap rates, or LLM output quality, and no such number appears in this paper.

\textbf{Contributions.} (1)~A code-grounded description of \RIE's architecture, data model and pipelines, including an audit of what is implemented, validated and merely documented. (2)~A reproducible harness (fetch emulator, synthetic ground-truth corpus, fault injection, single-factor metadata perturbation) that runs the unmodified modules, together with a claim-by-claim audit of every reported number against the raw results and an independent re-run. (3)~Empirical findings on latency structure, failure reporting, request amplification, and deduplication behaviour, notably that the repository's deduplicator is order-dependent (non-confluent) and that its fallback key fails under every single-factor metadata disagreement we tested except letter case. (4)~A prototype relaxed-key resolver, implemented only inside the harness, whose precision/recall trade-off is quantified. (5)~A clearly labelled single live session of the real application, compared qualitatively with the emulated findings. \emph{Novelty statement:} the contributions are predominantly engineering and empirical; we do not propose a new algorithm, and union-find resolution and fielded matching are standard in record linkage~\cite{fellegi1969theory,elmagarmid2007duplicate,christen2012data}.

The remainder of the paper is organized as follows: \cref{sec:related} reviews related work, \cref{sec:arch} describes the system, \cref{sec:method} formalizes the pipeline and the experimental design, \cref{sec:impl} audits the implementation, \cref{sec:eval} reports experiments, and \cref{sec:disc,sec:limits,sec:concl} discuss, bound and conclude.

\section{Related Work}
\label{sec:related}

\textbf{Open scholarly metadata.} OpenAlex was introduced as an open replacement for Microsoft Academic Graph~\cite{priem2022openalex}; the Semantic Scholar corpus and data platform expose papers, citation edges and full-text-derived fields~\cite{lo2020s2orc,kinney2023semantic}; Crossref aggregates publisher-deposited DOI metadata~\cite{hendricks2020crossref}; Europe~PMC and PubMed cover the life sciences~\cite{ferguson2021europepmc,sayers2022eutilities}. Comparative studies show non-trivial differences in coverage and reference completeness among bibliographic sources~\cite{visser2021large,alperin2024analysis} and in their suitability for systematic searching~\cite{gusenbauer2020which}. Only part of the literature is openly accessible (an estimated 28\,\% or more in a 2018 study~\cite{piwowar2018state}), which motivates \RIE's per-provider PDF-link handling. These studies evaluate the sources themselves rather than a local client that merges them.

\textbf{Federated search and tail latency.} Querying several independent engines and merging the results is the classical federated- (meta-) search problem, whose main sub-problems are resource description, resource selection and result merging~\cite{shokouhi2011federated}; rank-fusion methods such as reciprocal rank fusion combine per-source rankings~\cite{cormack2009reciprocal}. \RIE{} performs no score fusion: it keeps the top-$k$ of each provider and re-sorts the union by year or citation count (\cref{sec:arch}). A synchronous fan-out that waits for every backend is exposed to straggler effects: occasional slow components can dominate the overall latency of a fan-out service, which is the central concern of ``tail-tolerant'' design~\cite{dean2013tail}. We examine that exposure for \RIE{} concretely in \cref{sec:eval}.

\textbf{Duplicate detection.} Record linkage was formalized probabilistically by Fellegi and Sunter~\cite{fellegi1969theory}; surveys and textbooks catalogue field-similarity metrics, indexing (blocking) and classification techniques for duplicate detection~\cite{elmagarmid2007duplicate,christen2012data}. Bibliographic de-duplication has been studied in the systematic-review setting: a multi-stage, fielded procedure for a reference manager has been described~\cite{bramer2016dedup}, and a purpose-built tool was reported to detect 42.9\,\% more duplicates than that manager's automatic de-duplication on a 1\,988-citation benchmark~\cite{rathbone2015better}. \RIE{} uses exact-equality keys (DOI, \code{source:source\_id}, and a hash of title, first author and year). Equality keys are fast and precise but brittle under metadata variation; the experiments in \cref{sec:eval} quantify this brittleness for \RIE{} specifically.

\textbf{LLM-assisted literature analysis.} Retrieval-augmented generation grounds a generator in retrieved passages~\cite{lewis2020retrieval,gao2023retrieval}; PaperQA and PaperQA2 apply this to full-text scientific articles with evidence gathering and cited answers~\cite{lala2023paperqa,skarlinski2024language}; scite classifies the intent of citation statements~\cite{nicholson2021scite}. Unsupported generation (``hallucination'') is a documented failure mode of language generation~\cite{ji2023survey}, including fabricated references in literature-review writing~\cite{tang2025llmreview}. \RIE's analysis path is far simpler than these systems: it sends only the title and abstract plus a free-text instruction to a hosted open-weight model (default \code{openai/gpt-oss-120b}~\cite{openai2025gptoss}) and performs no retrieval, grounding or verification. We evaluate only its request scheduling and construction, not output quality.

\textbf{Positioning.} We do not benchmark \RIE{} against other tools, and we make no comparative performance claim. The paper's purpose is to characterize one system rigorously, with the harness and negative findings made available for reuse.

\section{System Architecture}
\label{sec:arch}

\subsection{Process model}
\RIE{} follows Electron's multi-process design (\cref{fig:arch}). Renderer windows (the main workbench and a separate editor window) run with \code{contextIsolation} enabled and \code{nodeIntegration} disabled; they reach the main process only through the \code{window.electronAPI} object that \code{preload.js} exposes via \code{contextBridge}, with namespaces \code{library}, \code{papers}, \code{ai}, \code{document}, \code{window} and \code{settings}. The main process (\code{electron-main.js}, plus \code{main/ipc/document-ipc.js}) registers one \code{ipcMain.handle} channel per operation and delegates to service modules. \code{paper-service.js} is the sole intermediary to ingestion, the database and the filesystem; \code{ai-service.js} wraps the hosted LLM endpoint; \code{document-service.js} spawns Pandoc for export. User-supplied API keys are persisted in a plaintext \code{settings.json} in the Electron \code{userData} directory and mirrored into \code{process.env}.

\subsection{Source adapters and the canonical record}
Each provider has an \emph{adapter} (HTTP request and parsing only) and a \emph{normalizer} (mapping to a canonical record, never throwing, missing fields $\to$ \code{null}). The registry in \code{search-orchestrator.js} binds names to pairs of functions, so adding a provider requires one entry plus its adapter and normalizer modules. The canonical record has twelve fields: \code{id}, \code{source}, \code{source\_id}, \code{title}, \code{abstract}, \code{authors[]}, \code{year}, \code{venue}, \code{doi}, \code{url}, \code{pdf\_url}, \code{citation\_count}. Provider-specific handling visible in the code (\cref{tab:sources}) includes reconstruction of OpenAlex abstracts from an inverted index, stripping of JATS markup from Crossref abstracts, a Crossref look-up for each Europe~PMC hit that carries a DOI, to find a direct PDF link, and deliberate omission of PubMed PDF links (documented in the code as blocked by an anti-bot challenge).

\subsection{Search pipeline}
A call \code{searchAndStore(q, sources, k, sortBy)} (\cref{fig:flow}) validates source names, dispatches all adapters concurrently with \code{Promise.allSettled}, normalizes each provider's raw items, ranks them and keeps the top $k$ per provider, deduplicates the union, assigns \code{randomUUID} identifiers \emph{after} deduplication, ranks the union again, and inserts the records into PostgreSQL. Ranking is by publication year then citation count (\code{sortBy=date}) or the reverse (\code{sortBy=citations}); records with missing values sort last. Provider relevance order is therefore \emph{not} preserved: for \code{date}, the candidate pool is the $3k$ most relevant OpenAlex results and the $3k$ most recent arXiv results, which are then re-sorted by year. The orchestrator returns the ranked list plus \code{providerStats} and \code{providerFailures} for display.

\subsection{Persistence}
A single table \code{papers} stores the canonical record plus \code{created\_at} and \code{local\_pdf\_path}; \code{authors} is JSONB; \code{UNIQUE(source, source\_id)}, a unique partial index on \code{doi}, and an index on \code{created\_at} are created idempotently at start-up. Insertion is one \code{INSERT \ldots{} ON CONFLICT DO NOTHING} per record followed by a \code{SELECT} that finds the surviving row (by \code{source, source\_id} or DOI) and overwrites the in-memory \code{id} with the database identifier, so repeated searches return stable identifiers. The README additionally mentions \code{analyses} and \code{collections} tables and ``indexed full-text fields''; the schema module creates neither (\cref{sec:impl}).

\subsection{PDF acquisition, library and AI analysis}
\code{downloadPaperPdf} fetches a PDF, rejects \code{text/html} responses and bodies lacking the \code{\%PDF-} magic bytes, writes to a temporary file outside the library, copies it to \code{raw\_papers/<title>{-}{-}<uuid>.pdf}, and records a workspace-relative path. \code{getLibraryPapers} lists \code{raw\_papers/}, loads \emph{all} rows of \code{papers}, and associates files with rows by UUID suffix, stored path, or a substring test on \code{source\_id}; unmatched files are shown as ``External Document''. AI analysis is user-triggered and serial: for each paper the renderer calls \code{ai:analyzePaper}, which POSTs a chat-completion request (system prompt, then a user message containing title, abstract and a free-text task; temperature~0.3, \code{max\_tokens}~1024) to the Groq endpoint with a minimum interval between request starts (default 2\,s) and exponential back-off on HTTP~429. Each answer is written to \code{analysis/<title>.md}.

\section{Methodology}
\label{sec:method}

\subsection{Formal model of the search pipeline}
Let $\mathcal S$ be the selected providers and $T_s$ the time adapter $s$ needs to \emph{settle} (resolve or reject). Because the orchestrator awaits \code{Promise.allSettled}, the time to first result is
\begin{equation}
T_{\text{search}} = \max_{s\in\mathcal S} T_s + \varepsilon_{\text{local}},
\label{eq:tsearch}
\end{equation}
where $\varepsilon_{\text{local}}$ is the local normalize--deduplicate--rank cost. For adapters with dependent requests, and a per-request service time $L$, the code implies
\begin{align}
T_{\text{oa}} = T_{\text{s2}} = T_{\text{cr}} &= L, \quad T_{\text{ax}} = w_{\text{ax}} + L, \nonumber\\
T_{\text{epmc}} &= L + \max_{i\le k} L^{\text{cr}}_i \approx 2L, \nonumber\\
T_{\text{pm}} &= \max(L,\rho) + L, \quad \rho = 0.35\,\text{s},
\label{eq:adapters}
\end{align}
where $w_{\text{ax}}=\max(0,\,3\,\text{s}-\Delta)$ is the arXiv throttle wait given $\Delta$ seconds since the previous arXiv call started (state is module-global, so it persists across searches), and the Europe~PMC enrichment look-ups run concurrently. \cref{eq:adapters} assumes a cold start: the PubMed adapter's spacing state is also module-global, so a search begun less than $\rho$ after the previous PubMed request would wait for its first request as well [C]. With a uniform $L$ this gives $T_{\text{search}} \approx \max(2L,\ \max(L,\rho)+L)$; at $L{=}0$ the PubMed spacing alone sets a floor of $\rho$. An upper bound on the worst case follows from the timeouts in \cref{tab:sources}: $T_{\text{search}} \lesssim \max(3{+}30,\ 25,\ 15{+}3,\ 2{+}2{\cdot}15)\approx 33$\,s, attained when an adapter hangs. The upstream request count for a search is $N_{\text{req}} = 1{+}1{+}1{+}1{+}(1{+}n_{\text{epmc}}){+}2 = 7+n_{\text{epmc}}$ where $n_{\text{epmc}}\le k$ is the number of Europe~PMC hits that carry a DOI.

\subsection{Deduplication as implemented}
For a canonical record $p$ define three keys: $\kappa_{\text{doi}}(p)$ (the lower-cased DOI without resolver prefix, if any), $\kappa_{\text{src}}(p)=(\text{source},\text{source\_id})$ (if \code{source\_id} is non-empty), and $\kappa_{h}(p)=\operatorname{SHA256}(\text{lc}(\text{title})\,|\,\text{lc}(\text{first author})\,|\,\text{year})$. Records are processed in input order; a record is a duplicate of the \emph{first} retained record that has an equal key (tested in the order DOI, source, hash), in which case missing \code{pdf\_url}, \code{abstract}, \code{venue}, \code{doi} and \code{citation\_count} of the retained record are filled from the duplicate. Otherwise the record is retained and \emph{its} keys are registered. Two properties follow directly from the code and are tested experimentally.

\emph{Property~1 (order dependence).} A duplicate's keys are not registered, even when they differ from the retained record's. Consider records $a,b,c$ of one work with $\kappa_h(a)=\kappa_h(b)\ne\kappa_h(c)$, $a$ without DOI, and $\kappa_{\text{doi}}(b)=\kappa_{\text{doi}}(c)$. For input order $(a,b,c)$: $b$ merges into $a$ via $\kappa_h$, $b$'s DOI is not registered, so $c$ matches nothing and two records are output; for order $(b,a,c)$, $a$ merges into $b$ via $\kappa_h$ and $c$ merges via the DOI, giving one record. The result thus depends on provider order and per-provider ranking, i.e., the procedure is not confluent. A transitive-closure (union-find) resolution over the same keys is order independent.

\emph{Property~2 (no negative DOI evidence).} The lookup chain evaluates $\kappa_h$ even if both records carry DOIs that differ, so differing DOIs never prevent a merge.

\emph{Cost.} Each record costs $O(1)$ hash-table operations plus one SHA-256, so the procedure is $O(n)$.

\subsection{Expected residual duplicates}
For a same-work pair in which at least one record lacks a DOI (typical for arXiv, \cref{tab:sources}) and the source identifiers differ, a merge happens only if the strict keys coincide. Writing $p_t$, $p_a$, $p_y$ for the probabilities that the normalized title, first-author string and year agree, and \emph{assuming independence}, $\Pr[\text{merge}]\approx p_tp_ap_y$ and the expected number of residual duplicates among $M$ such pairs is $M(1-p_tp_ap_y)$. We do not estimate $p_t,p_a,p_y$ for real providers; \cref{sec:eval} instead measures the response of the implementation to controlled values of each factor.

\subsection{AI-analysis scheduling}
With minimum start interval $\tau$ (default $2$\,s) and per-request latency $L_i$, the loop waits $\max(0,\tau-L_{i-1})$ after request $i{-}1$ returns, so starts are separated by $\max(L_{i-1},\tau)$ and a batch of $N$ papers takes $T_N=\sum_{i<N}\max(L_i,\tau)+L_N$ plus retries. On HTTP~429 the $a$-th retry waits $2^{a}\,\text{s}+U[0,0.5)\,\text{s}$ for $a\le m$ (default $m=3$), so $k\le m$ consecutive 429s add $\sum_{a=1}^{k}(2^a+0.25)$\,s in expectation; the $(m{+}1)$-th consecutive 429 raises the error.

\subsection{Experimental design}
\textbf{Harness.} Experiments run the repository modules unmodified under Node.js; the only substitution is \code{globalThis.fetch}, replaced by an emulator that (i)~routes by host to one of six provider mimics or the Groq endpoint, (ii)~renders records of a synthetic ground-truth corpus into the raw response shape that the corresponding normalizer reads (derived from the normalizers and the repository's own test fixtures, \emph{not} from recorded live traffic), (iii)~injects a configurable latency, and (iv)~injects faults (HTTP~500/429, network error, hang until the adapter's abort signal). Database experiments use a real PostgreSQL~16.15 server on the loopback interface with the repository's schema module. Every random choice is seeded. Two experiments call library functions directly rather than through the orchestrator: part~D of E2 replicates orchestrator steps~1--3 by calling the same adapters, normalizers and ranker (its output was checked against the real orchestrator), and E1 times \code{xml2js} parsing with the adapters' parser options. A separate script (\code{verification/verify\_module\_usage.mjs}) confirms that no tracked application file differs from the baseline commit, that the replicated pipeline returns the same record set \emph{and} ranked order as the real orchestrator for three further queries, and that the synthetic renderings survive a round trip through the real normalizers (200 of 200 records agree with ground truth in every field for every provider, except the first-author string for Europe~PMC, which is rendered as ``Surname Initial'' by design).

\textbf{Synthetic corpus.} Works have unique titles (a numeric token guarantees no accidental collisions), 2--6 authors including names with diacritics, a DOI, a PMID, an arXiv identifier for about half the works, and a preprint year equal or one year earlier than the journal year. Because identity is known, merge outcomes are scored exactly. \emph{The corpus says nothing about real overlap rates.}

\textbf{Metrics.} \emph{Pairwise merge recall} is the fraction of same-work record pairs collapsed to one record. \emph{False merges} count distinct-work pairs collapsed. \emph{Residual duplicates} are $|\text{output}|-|\text{distinct works}|$. Timings use \code{performance.now()}; we report medians (with quartiles where $n\ge5$), discarding warm-up repetitions. Latency in the emulator is an injected parameter; measured wall-clock is compared with the models of the previous subsections.

\textbf{Platform [S].} 4 vCPU Intel Xeon 2.3\,GHz, 16\,GB RAM, Ubuntu 24.04.5, Node.js v22.23.4, PostgreSQL 16.15, \code{pg} 8.20.0, \code{xml2js} 0.6.2 (recorded by \code{experiments/env\_info.mjs}); a single cloud machine, with the Electron shell and GUI not run. Experiments that measure wall-clock time were run with no other load. \textbf{Variants.} Besides the repository's \code{deduplicate()}, two harness-only variants are evaluated: \textsc{uf-repo} (union-find over the same three keys) and \textsc{uf-relaxed} (union-find over DOI, \code{source:id}, and a relaxed key: diacritic-folded alphanumeric title, first-author surname and first initial, linked only if years differ by at most one). The relaxed key is a prototype for quantifying trade-offs, not a proposal evaluated on real data.

\subsection{Evidence classes and the live session}
To keep simulated and live evidence apart, every result is assigned one of four classes (\cref{tab:evidence}); table and figure captions carry the label. The \textbf{live session [L]} is a set of observations that the author recorded from the Windows desktop build of \RIE{} using its own in-app logs: one query (``transformers''), one session, no repetitions. We report these observations exactly as recorded, derive only arithmetic quantities from them (e.g., a mean per paper), and state which quantities were \emph{not} recorded. They were not reproduced in the cloud, are not benchmarks, and are used only to check whether the emulated findings are \emph{qualitatively} consistent with the real application. The AI timing covers analysis and saving of reports, not summary accuracy, and the editor timing is an approximate observation.

\subsection{RQ1: search latency, throttles and failure containment [S]}
\textbf{Latency structure.} We issued a six-provider search ($k{=}10$, each run after $\ge$3.3\,s of idleness so that the arXiv throttle is not engaged) with the same injected latency $L$ for every upstream request. \cref{fig:latency} shows that the observed median equals the parallel model of \cref{eq:tsearch,eq:adapters} to within 4--11\,ms at every $L$ (e.g., 2\,011\,ms observed vs.\ 2\,000\,ms predicted at $L{=}1$\,s), and is far below the sum-of-adapters and fully serial alternatives (8\,000 and 17\,000\,ms at $L{=}1$\,s). At $L{=}0$ the search still takes $\approx$358\,ms: the 350\,ms spacing between PubMed's two requests is a floor that no upstream speed can remove. Interquartile ranges were about 1\,ms or less, so the emulator-driven runs are highly repeatable at that precision; this says nothing about real network jitter.

\textbf{Back-to-back searches.} The arXiv adapter's 3\,s spacing is module-global state. \subsection{RQ2: deduplication [S]}
\textbf{Single-factor disagreement.} For up to 500 works we built two records of the same work, one from an OpenAlex-style rendering (with DOI) and one from a record that lacks a DOI (arXiv-style, via the real arXiv normalizer), differing in one metadata factor at a time; \cref{fig:dedup} reports the fraction merged. When both records carry the same DOI, every variant merges all pairs for every perturbation (recall 1.00; not plotted). Without a shared DOI the repository's \code{deduplicate()} merges only metadata-identical records and records differing in letter case: a one-year difference in publication year, any change of first-author format (``A.\ Surname'', ``Surname A''), a trailing period, a changed subtitle separator, a dropped subtitle, diacritic folding of the first author, and reversed author order each give recall 0.00. The \textsc{uf-repo} variant behaves identically on these pairs, as expected, since it uses the same keys. The relaxed-key prototype restores recall 1.00 for all but two probes, reversed authors (the first-author key changes) and a dropped subtitle (the title key changes), which require different evidence.

\subsection{RQ3: local cost and scaling [S]}
\textbf{Normalization and parsing.} Normalizers cost between 3.1 and 6.6\,\textmu s per record, and parsing an arXiv Atom response of 100 entries (79\,kB) or a PubMed EFetch response of 100 entries (122\,kB) took 2.4--3.8\,ms and 5.7--7.4\,ms respectively (ranges over two independent executions of the full sweep, \cref{sec:eval}-A). Microsecond-level timings were the least stable measurements in the study: individual providers differed by up to 45\,\% between the two executions (e.g., OpenAlex 6.6 vs.\ 3.6\,\textmu s), so we make no ranking claim among providers and treat these figures as orders of magnitude. Orchestration of four JSON providers (fetch emulation, parse, normalize, rank, deduplicate, UUIDs) took about 5\,ms at $k{=}10$, about 19\,ms at $k{=}100$ and 32--43\,ms at $k{=}200$ (medians, $n{=}15$ per setting, two executions), growing about linearly with the 40--800 candidates. Local compute is thus negligible next to the adapter timeouts of 15--30\,s and to any injected latency we used.

\textbf{Persistence.} On a local PostgreSQL~16 instance (\cref{tab:db}), \code{searchAndStore} adds about 0.5--0.7\,ms per returned paper for the sequential \code{INSERT} plus \code{SELECT} (two round trips per record), i.e., 28\,ms for 40 papers and 188\,ms for 355. Repeating the identical search (all rows conflict) costs roughly half, returns identical identifiers (checked for all four limits), and leaves the row count unchanged, confirming that the \code{ON CONFLICT DO NOTHING}\,+\,re-select design provides stable identifiers. Over a network the two round trips per record would dominate; we did not measure this.

\subsection{RQ4: AI-analysis client [S]}
\textbf{Scheduling.} With the shipped 2\,s interval, six papers took 10.2, 11.0, 12.0 and 18.0\,s for injected model latencies of 0.2, 1, 2 and 3\,s; the model $5\max(L,\tau)+L$ predicts 10.2, 11.0, 12.0 and 18.0\,s (\cref{fig:ai}a), and start-to-start gaps had a median of 2\,002, 2\,001, 2\,003 and 3\,004\,ms. The loop is strictly serial, so throughput is bounded by $\max(L,\tau)$ per paper regardless of what the provider would allow.

\textbf{Retry behaviour.} Success after one, two or three consecutive 429 responses took 2.2--2.3, 6.2--6.7 and 14.4--14.8\,s respectively ($n{=}3$ each), matching $\sum(2^a+0.25)$\,s; with four consecutive 429s the client issued four requests in 14.7--14.9\,s and then threw (\cref{fig:ai}b). HTTP 400, 401, 500 and 503 responses were \emph{not} retried (one request each), so transient server errors fail a paper immediately; \code{Retry-After} is ignored. Inside \code{processPapers}, an injected failure at the third of five papers was isolated (4 succeeded, 1 failed, the failure recorded with its title).

\textbf{Prompt construction.} The user message is \code{Paper Title: \${title}\textbackslash nAbstract: \${abstract}\textbackslash n\textbackslash nTask: \${prompt}} with no null handling. For a paper whose abstract is \code{null} (the normalizers' value for a missing abstract; arXiv, PubMed and Crossref records can lack one) the model receives the literal text ``\code{Abstract: null}'', for an absent field ``\code{Abstract: undefined}'', and a 20\,000-word abstract is sent whole (100\,060 characters) with no truncation. Responses are requested with \code{temperature} 0.3 and \code{max\_tokens} 1024 for model \code{openai/gpt-oss-120b}. Whether a model given ``\code{Abstract: null}'' fabricates content is not measured here; the prompt gives it no instruction to refuse.

\section{Discussion}
\label{sec:disc}

\textbf{Answers to the research questions.} \emph{RQ1:} search latency is the maximum, not the sum, of adapter latencies, but the maximum includes adapter-internal serialization (PubMed spacing, Europe~PMC enrichment, arXiv throttle) and has no deadline, so one hung provider holds back all results until its timeout (\cref{sec:eval}); failure containment is good for five providers and misreported for arXiv. \emph{RQ2:} the deduplicator reliably merges records that share a DOI and nothing else; for DOI-less records it merges only metadata-identical strings, and the outcome depends on input order. \emph{RQ3:} local compute is negligible next to network time, but the library view re-reads and scans the whole table and scales with rows~$\times$ files in its fallback path. \emph{RQ4:} the AI client enforces a $\tau$-spaced serial schedule and bounded back-off for 429 only; it sends the literal string \code{null} for a missing abstract. The single live session (\cref{sec:live}) did not contradict any of these emulated findings: a rate-limited provider did not block the others, and the observed 27\,s for eight analyses is compatible with a serial loop.

\textbf{Emulated versus live evidence.} The emulated experiments establish \emph{mechanisms} (what the code does when a provider is slow, fails, or disagrees on metadata) under controlled conditions, with exact counts that an independent re-run reproduced. The live session adds what they cannot: evidence that the full pipeline works against real providers, a real database initialization, real PDF hosts and the real Groq endpoint on a Windows desktop. It cannot establish rates, distributions or generality, and the two kinds of evidence answer different questions, so we compare them only qualitatively (\cref{tab:livecmp}). Two quantities the live session would need to record to allow quantitative comparison are the per-provider latency of a search and the per-paper latency of the AI call; the application records neither (\code{providerStats} holds only status and counts), so a future live protocol would need timestamps added around the adapter calls and the AI request.

\textbf{Engineering recommendations tied to evidence.} (1)~Make adapter failure handling uniform: the arXiv adapter should reject on HTTP errors and timeouts like the other five. (2)~Add a global deadline with progressive delivery, since a single hung provider costs 15--33\,s, whereas healthy emulated providers settle in well under a second (real settle times were not measured); because hedged requests~\cite{dean2013tail} would multiply load on rate-limited free APIs, a deadline plus partial results is the proportionate response. (2b)~Configure a Semantic Scholar API key, as the code's own error message advises, since an unauthenticated provider was rate limited in the live session. (3)~Replace first-match deduplication by transitive closure over registered keys of \emph{all} records, which makes the output order independent, costs the same $O(n)$ (\cref{fig:scaling}), and lets a DOI veto and empty-field guards be added. (4)~Any relaxation of the fallback key (diacritic folding, punctuation-insensitive titles, surname/initial authors, $\pm1$ year) recovers the DOI-less cases but admits same-initial/same-title false merges, so it should be adopted only with a labelled evaluation on real provider data and extra evidence such as author-list overlap. (5)~Bound or defer the Europe~PMC enrichment fan-out ($k$ extra Crossref requests per search). (6)~Guard null abstracts and over-long inputs in the prompt, honour \code{Retry-After}, and retry transient 5xx responses. (7)~Batch database inserts and index the library scan if libraries grow beyond a few thousand records. (8)~Call arXiv over HTTPS: \code{arxiv.js} uses a plain-HTTP URL, which an HTTPS-only egress proxy could not carry in our test environment [C]. These are suggestions derived from measured behaviour [S], the live session [L] and code inspection [C]; we did not implement them in the application, and we make no claim that they improve it, since no comparative evaluation was run.

\textbf{Engineering contribution vs.\ scientific novelty.} The system itself is an integration of existing services and techniques; its value is practical. The scientific content of this paper is limited to (i)~an explicit, tested latency model of a federated fan-out with adapter-internal throttling, (ii)~a demonstration that a common ``first match wins'' key-based deduplicator is non-confluent and a quantification of which metadata disagreements defeat equality keys, and (iii)~a reusable fault-injection harness. None of these is a new algorithm, and none establishes retrieval or summarization quality.

\section{Limitations and Threats to Validity}
\label{sec:limits}

\textbf{Emulated upstreams and one live session.} Upstream behaviour in all [S] experiments is emulated. Provider latency, rate-limit behaviour, error rates, payload quirks and genuine cross-provider overlap are therefore unmeasured there; injected latencies are parameters, not estimates of real services, and agreement with \cref{eq:tsearch,eq:adapters} shows that the code behaves as modelled, not that real searches take any particular time. The only live evidence [L] is one user-recorded session (one query, no repetition) taken from in-app logs and not independently reproduced; it did not record search latency, per-paper AI latency, the configured limit, PubMed participation, PDF counts, or system details (\cref{sec:live}), the AI timing covers processing and saving and not accuracy, and the editor timing is approximate. The LLM endpoint was likewise only emulated in the cloud: we measured scheduling and request construction, not output quality.

\textbf{Reconstructed payloads.} Raw provider responses are rendered from the fields that the repository's normalizers read and from its own test fixtures. If real responses differ (e.g., author-name conventions, title punctuation, year semantics), residual-duplicate rates will differ. Single-factor perturbations (\cref{fig:dedup}) are deterministic properties of the key definitions and do not depend on assumed rates, but the mixed scenario of \cref{tab:e2d} depends on the assumed preprint-year skew (40\,\% of arXiv-bearing works) and abbreviated Europe~PMC author strings, and must be read as illustrative.

\textbf{Synthetic corpus and no relevance judgments.} Titles are unique by construction, which removes natural-language near-duplicates (e.g., translated titles, errata, ``Part~I/II'' series), so false-merge rates for the strict key are lower bounds on what real corpora would show and those for the relaxed key are probes, not estimates. We evaluate no query relevance, no recall against a gold standard, and no ranking quality; the year-based re-ranking may discard relevant older papers, which we neither confirm nor refute.

\textbf{Prototype variants.} \textsc{uf-repo} and \textsc{uf-relaxed} exist only in the harness; \textsc{uf-relaxed} was designed after inspecting the failure cases and tuned to nothing else, but it is untested on real data and deliberately lacks safeguards (author-list overlap, DOI veto) that a production resolver would need.

\textbf{Environment.} One machine (4 vCPU), one Node.js version, one PostgreSQL version on loopback; absolute microsecond-level timings will differ elsewhere, and PostgreSQL latency over a network would change \cref{tab:db}. The Electron GUI, the editor, Pandoc export, and the PDF download path against real publishers were not exercised; the security posture (plaintext key storage, broad IPC surface) was read from the code, not tested. Code inspection also shows that the PDF download \code{fetch} has no timeout or size limit; we did not test this.

\section{Conclusion}
\label{sec:concl}

We characterized the Research Intelligence Engine by reading its code and by running its unmodified modules against an emulated upstream environment and a real PostgreSQL server. Search latency follows the maximum of adapter latencies to within about 11\,ms in our sweep, but provider-internal throttles impose a 350\,ms floor and up to $\approx$2.6\,s of extra delay for back-to-back searches, a hung provider delays the whole result set until its timeout, and the arXiv adapter reports failures as empty successes. The deduplicator is order dependent and recovers no DOI-less duplicate under any single-factor metadata disagreement except letter case; a union-find resolver over the same keys is order independent at equal cost, and a relaxed-key prototype recovers most DOI-less cases at the price of measurable false merges. Local compute and persistence costs are small. The AI client schedules serially with a 2\,s interval and bounded exponential back-off, but silently sends \code{null} for missing abstracts. A single user-recorded live session on a Windows desktop (four providers returning two papers each, Semantic Scholar rate limited, eight papers analyzed and saved in 27\,s) was consistent with these findings without being a benchmark. What remains open is everything that requires repeated live measurement: real latency distributions, real overlap and duplicate rates, retrieval effectiveness, and the quality of LLM analyses. The accompanying harness is intended to make such measurements easy to add once network access is available.

\section*{Reproducibility and availability}
All files are in the \code{paper\_exp/} directory of the repository: \code{main.tex}, \code{references.bib}, \code{figures/} (SVG sources, generators, PDF conversions), \code{experiments/} (harness; \code{run\_all.sh} reproduces every [S] result in about 25 minutes, mostly deliberate waits), \code{results/} (raw JSON for every table and figure, plus \code{environment.json}), \code{logs/}, and \code{verification/} (claim-by-claim audit, module-usage report, an independent re-run, and the bibliographic audit). Requirements: Node.js~$\ge$18, \code{npm ci --omit=dev --ignore-scripts}, and a local PostgreSQL with database \code{rie\_bench} for E4. The AI experiments use a dummy key and an emulated endpoint; no credential was used. The repository tests [R] need network access and, in the cloud sandbox, the proxy variable and shim described in Section~V (\code{logs\_online/}); the live observations [L] cannot be reproduced in the cloud; they are recorded in \cref{tab:live} as reported by the author from the in-app logs.
