\title{Research Intelligence Engine: Architecture and Empirical Characterization of a Desktop Multi-Source Scholarly Retrieval and LLM-Annotation Pipeline}

\author{\IEEEauthorblockN{Suryavansh Jaggi}
\IEEEauthorblockA{IILM University, Greater Noida\\
suryavansh.jaggi.cs27@iilm.edu}}

\maketitle


\begin{abstract}
We characterize the Research Intelligence Engine (RIE), an open-source Electron/PostgreSQL desktop application that fans a query out to six scholarly-metadata providers, normalizes and deduplicates the results, stores them, and sends abstracts to a hosted LLM. Controlled experiments run RIE's unmodified modules against a deterministic emulator of the upstream APIs and a real PostgreSQL server. Search latency tracks the slowest adapter within 11\,ms, but provider throttles impose a 350\,ms floor and up to $\approx$2.6\,s of delay on back-to-back searches, a hung provider blocks all results until its 15--30\,s timeout, and arXiv failures are reported as empty successes. The deduplicator is order dependent (1\,000 or 2\,000 output records for identical inputs) and merges DOI-less records only when metadata strings match up to letter case. The AI client is serial, spaced by 2\,s, retries only HTTP~429, and sends the literal text ``null'' for missing abstracts. A separate, single, user-recorded live session on a Windows desktop (four providers returned two papers each, Semantic Scholar returned HTTP~429, eight papers analyzed and saved in 27\,s) is consistent with these findings but is not a benchmark. No retrieval-quality or LLM-quality claims are made.
\end{abstract}

\begin{IEEEkeywords}
scholarly metadata aggregation, federated search, record deduplication, LLM-assisted literature analysis, Electron, fault injection
\end{IEEEkeywords}

\section{Introduction}
\label{sec:intro}

Literature tools increasingly query open scholarly-metadata services directly: OpenAlex~\cite{priem2022openalex}, Semantic Scholar~\cite{lo2020s2orc,kinney2023semantic}, Crossref~\cite{hendricks2020crossref}, Europe~PMC~\cite{ferguson2021europepmc}, PubMed via NCBI E-utilities~\cite{sayers2022eutilities}, and arXiv~\cite{arxivapi}. Their coverage and metadata differ~\cite{visser2021large,gusenbauer2020which,alperin2024analysis}, so a multi-source client must reconcile schemas, tolerate partial failure and rate limits, and remove cross-provider duplicates. LLMs are also used to summarize papers, with a documented risk of unsupported output~\cite{ji2023survey,tang2025llmreview}.

The Research Intelligence Engine (\RIE) packages these functions in one desktop workflow: concurrent retrieval from six providers, normalization, in-memory deduplication, PostgreSQL persistence with PDF acquisition, abstract-level LLM analysis, and a Markdown/\LaTeX{} editor. Version~1.0.0 has no published evaluation, and its README describes a narrower, partly different system than the code (\cref{sec:impl}). We ask:
\textbf{RQ1} how the fan-out determines search latency and failure containment;
\textbf{RQ2} how reliably the three-key deduplication resolves duplicates;
\textbf{RQ3} what local components cost and how they scale;
\textbf{RQ4} how the AI client schedules, retries and builds its prompt.

\textbf{Evidence.} The cloud sandbox used for the experiments blocked the scholarly APIs and the LLM endpoint, so the real modules were run unmodified against a deterministic upstream \emph{emulator} with injected latency and faults, and a real PostgreSQL~16 server; these results are labelled \textbf{[S]}. One live session of the Windows desktop build, recorded by the author from in-app logs, is labelled \textbf{[L]} and reported separately (\cref{tab:evidence}). We did not measure real latency distributions, retrieval effectiveness, real overlap rates, or LLM output quality.

\textbf{Contributions.} (1)~A code-grounded description and implementation audit of \RIE. (2)~A reproducible harness (fetch emulator, ground-truth corpus, fault injection, single-factor metadata perturbation) with a claim-by-claim audit and an independent re-run. (3)~Findings on latency structure, failure reporting, request amplification and deduplication, notably that the deduplicator is non-confluent and its fallback key fails under every tested single-factor disagreement except letter case. (4)~A harness-only relaxed-key resolver with a quantified precision/recall trade-off. (5)~A labelled live session compared qualitatively with the emulated findings. The contributions are engineering and empirical; union-find resolution and fielded matching are standard record-linkage techniques~\cite{fellegi1969theory,elmagarmid2007duplicate,christen2012data}.

\section{Related Work}
\label{sec:related}

\textbf{Open scholarly metadata.} OpenAlex replaced Microsoft Academic Graph as an open index~\cite{priem2022openalex}; Semantic Scholar exposes papers, citations and full-text-derived fields~\cite{lo2020s2orc,kinney2023semantic}; Crossref aggregates DOI metadata~\cite{hendricks2020crossref}; Europe~PMC and PubMed cover the life sciences~\cite{ferguson2021europepmc,sayers2022eutilities}. Their coverage and completeness differ~\cite{visser2021large,alperin2024analysis,gusenbauer2020which}, and only part of the literature is open access (28\,\% or more~\cite{piwowar2018state}).

\textbf{Federated search.} Merging results of independent engines is federated search~\cite{shokouhi2011federated}, often with rank fusion~\cite{cormack2009reciprocal}; \RIE{} does no fusion. Waiting for every backend exposes a fan-out to stragglers~\cite{dean2013tail}.

\textbf{Duplicate detection.} Record linkage theory and techniques are surveyed in~\cite{fellegi1969theory,elmagarmid2007duplicate,christen2012data}; for systematic reviews, fielded procedures~\cite{bramer2016dedup} and a dedicated tool finding 42.9\,\% more duplicates than a reference manager~\cite{rathbone2015better} have been reported.

\textbf{LLM-assisted literature analysis.} RAG~\cite{lewis2020retrieval,gao2023retrieval}, PaperQA/PaperQA2~\cite{lala2023paperqa,skarlinski2024language} and scite~\cite{nicholson2021scite} ground or classify scientific text; \RIE{} sends only title, abstract and an instruction to an open-weight model (\code{openai/gpt-oss-120b}~\cite{openai2025gptoss}) without grounding.

\section{System Architecture}
\label{sec:arch}

\textbf{Process model.} \RIE{} follows Electron's multi-process design (\cref{fig:arch}). Renderer windows (workbench and editor) run with \code{contextIsolation} on and \code{nodeIntegration} off and reach the main process only through \code{window.electronAPI} (namespaces \code{library}, \code{papers}, \code{ai}, \code{document}, \code{window}, \code{settings}) exposed by \code{preload.js}. IPC handlers delegate to \code{paper-service.js} (ingestion, database, files), \code{ai-service.js} and \code{document-service.js} (Pandoc). API keys are stored in a plaintext \code{settings.json} and mirrored into \code{process.env}.

\textbf{Adapters and canonical record.} Each provider has an \emph{adapter} (HTTP and parsing only) and a \emph{normalizer} (total function to a twelve-field record: \code{id}, \code{source}, \code{source\_id}, \code{title}, \code{abstract}, \code{authors[]}, \code{year}, \code{venue}, \code{doi}, \code{url}, \code{pdf\_url}, \code{citation\_count}; missing fields $\to$ \code{null}), bound in a registry so a provider is added with one entry. Provider-specific handling (\cref{tab:sources}) includes OpenAlex abstract reconstruction from an inverted index, JATS stripping for Crossref, a Crossref look-up for each Europe~PMC hit with a DOI to find a PDF link, and deliberate omission of PubMed PDF links.

\textbf{Search pipeline.} \code{searchAndStore(q, sources, k, sortBy)} (\cref{fig:flow}) dispatches all adapters with \code{Promise.allSettled}, normalizes, ranks and keeps the top $k$ per provider, deduplicates the union, assigns \code{randomUUID}s \emph{after} deduplication, re-ranks, and inserts into PostgreSQL. Ranking is by year then citations (or the reverse), missing values last, so provider relevance order is discarded. The result carries \code{providerStats} and \code{providerFailures}.

\textbf{Persistence, PDFs and AI.} One table \code{papers} holds the record plus \code{created\_at} and \code{local\_pdf\_path} (\code{authors} as JSONB; \code{UNIQUE(source, source\_id)}, unique partial index on \code{doi}). Each record is inserted with \code{ON CONFLICT DO NOTHING} and re-selected so repeated searches return stable identifiers. PDFs are validated (\code{\%PDF-}) and stored as \code{raw\_papers/<title>{-}{-}<uuid>.pdf}; \code{getLibraryPapers} loads \emph{all} rows and matches files by UUID, stored path or \code{source\_id} substring. AI analysis is serial: each paper becomes a chat-completion request (title, abstract, task; temperature~0.3, \code{max\_tokens}~1024) to Groq, with a minimum 2\,s interval and back-off on HTTP~429; answers go to \code{analysis/<title>.md}.

\section{Methodology}
\label{sec:method}

\textbf{Latency model.} With $T_s$ the settle time of adapter $s$, \code{Promise.allSettled} gives
\begin{equation}
T_{\text{search}} = \max_{s\in\mathcal S} T_s + \varepsilon_{\text{local}}.
\label{eq:tsearch}
\end{equation}
For a per-request service time $L$ the code implies
\begin{align}
T_{\text{oa}} = T_{\text{s2}} = T_{\text{cr}} &= L, \quad T_{\text{ax}} = w_{\text{ax}} + L, \nonumber\\
T_{\text{epmc}} &= L + \max_{i\le k} L^{\text{cr}}_i \approx 2L, \nonumber\\
T_{\text{pm}} &= \max(L,\rho) + L, \quad \rho = 0.35\,\text{s},
\label{eq:adapters}
\end{align}
where $w_{\text{ax}}=\max(0,\,3\,\text{s}-\Delta)$ is the arXiv throttle wait, $\Delta$ the time since the previous arXiv call (module-global state, persisting across searches; PubMed spacing is likewise global [C]). Hence $T_{\text{search}} \approx \max(2L,\ \max(L,\rho)+L)$, with a floor of $\rho$ at $L{=}0$, and, from the timeouts, $T_{\text{search}} \lesssim \max(3{+}30,\ 25,\ 15{+}3,\ 2{+}2{\cdot}15)\approx 33$\,s when an adapter hangs. A search issues $N_{\text{req}} = 7+n_{\text{epmc}}$ requests, $n_{\text{epmc}}\le k$ being the Europe~PMC hits with a DOI.

\textbf{Deduplication as implemented.} Keys are $\kappa_{\text{doi}}$ (lower-cased DOI without resolver prefix), $\kappa_{\text{src}}=(\text{source},\text{source\_id})$, and $\kappa_{h}=\operatorname{SHA256}(\text{lc}(\text{title})\,|\,\text{lc}(\text{first author})\,|\,\text{year})$. In input order, a record that shares a key (tested DOI, source, hash) with a \emph{retained} record is merged into it (filling missing \code{pdf\_url}, \code{abstract}, \code{venue}, \code{doi}, \code{citation\_count}); otherwise it is retained and its keys registered. Cost is $O(n)$.
\emph{Property~1 (order dependence):} a duplicate's keys are never registered. For records $a,b,c$ of one work with $\kappa_h(a)=\kappa_h(b)\ne\kappa_h(c)$, $a$ DOI-less and $\kappa_{\text{doi}}(b)=\kappa_{\text{doi}}(c)$, order $(a,b,c)$ yields two records but $(b,a,c)$ one; the procedure is not confluent, whereas union-find over the same keys is.
\emph{Property~2 (no negative DOI evidence):} $\kappa_h$ is evaluated even when both DOIs exist and differ.
For a same-work pair without a shared DOI, a merge requires equal title, author and year strings; under independence, $\Pr[\text{merge}]\approx p_tp_ap_y$. We do not estimate these probabilities for real providers but measure the response to controlled values of each factor.

\textbf{AI scheduling.} With start interval $\tau$ (2\,s) and latencies $L_i$, starts are separated by $\max(L_{i-1},\tau)$, so $T_N=\sum_{i<N}\max(L_i,\tau)+L_N$. The $a$-th retry after HTTP~429 waits $2^{a}\,\text{s}+U[0,0.5)\,\text{s}$ for $a\le m=3$, adding $\sum_{a=1}^{k}(2^a+0.25)$\,s in expectation; the $(m{+}1)$-th consecutive 429 throws.

\textbf{Harness.} Repository modules run unmodified under Node.js; only \code{globalThis.fetch} is replaced by an emulator that routes by host to six provider mimics or Groq, renders a synthetic ground-truth corpus into the raw shapes the normalizers read (derived from normalizers and repository fixtures, \emph{not} recorded traffic), and injects latency and faults (HTTP~500/429, network error, hang until abort). Database experiments use the repository schema on PostgreSQL~16.15 over loopback; randomness is seeded. Part~D of E2 replicates orchestrator steps~1--3 with the same modules, and E1 times \code{xml2js} with the adapters' options. A verification script confirms an unchanged application, identical record sets and order between replicated and real orchestrator on three queries, and 200/200 faithful normalizer round-trips per provider (Europe~PMC authors rendered ``Surname Initial'' by design).
\textbf{Corpus and metrics.} Works have unique titles, 2--6 authors (some with diacritics), DOI, PMID, an arXiv id for half, and a preprint year $\le$1 below the journal year. \emph{Pairwise merge recall} is the fraction of same-work pairs collapsed, \emph{false merges} distinct-work pairs collapsed, \emph{residual duplicates} $|\text{output}|-|\text{works}|$. Timings use \code{performance.now()}; we report medians (quartiles for $n\ge5$) after warm-up.
\textbf{Platform [S].} 4 vCPU Xeon 2.3\,GHz, 16\,GB, Ubuntu 24.04.5, Node.js v22.23.4, PostgreSQL 16.15, \code{pg} 8.20.0, \code{xml2js} 0.6.2; no other load; Electron GUI not run.
\textbf{Variants.} Besides \code{deduplicate()}, the harness evaluates \textsc{uf-repo} (union-find over the same keys) and \textsc{uf-relaxed} (union-find over DOI, \code{source:id}, and a diacritic-folded alphanumeric title + first-author surname and initial, linked if years differ by $\le$1), a prototype for quantifying trade-offs.
\textbf{Live session [L].} One query (``transformers''), one session, no repetition, recorded by the author from the Windows build's in-app logs. We report it as recorded, derive only arithmetic quantities, and use it solely for qualitative consistency checks.

\subsection{RQ1: latency, throttles and failure containment [S]}
\textbf{Latency structure.} For a six-provider search ($k{=}10$, after $\ge$3.3\,s idle) with a uniform injected latency $L$, the observed median matches the parallel model of \cref{eq:tsearch,eq:adapters} within 4--11\,ms (e.g., 2\,011 vs.\ 2\,000\,ms at $L{=}1$\,s), far below the sum-of-adapters and serial alternatives (8\,000 and 17\,000\,ms; \cref{fig:latency}). At $L{=}0$ a search still takes $\approx$358\,ms because of PubMed's 350\,ms spacing. IQRs were $\le$1\,ms.

\textbf{Back-to-back searches.} With $L{=}100$\,ms, a second search started immediately after the first took 2\,652\,ms (2\,642--2\,656) instead of 455\,ms; after gaps of 1, 2 and 3.5\,s it took 1\,650, 647 and 454\,ms, as $w_{\text{ax}}=\max(0,3-\Delta)$ predicts.

\textbf{Faults.} Injecting faults into one provider at a time (\cref{tab:faults}), an HTTP~500 or network error is reported correctly for five providers and the others' results are unaffected. \subsection{RQ2: deduplication [S]}
\textbf{Single-factor disagreement.} For up to 500 works we built two same-work records, an OpenAlex-style one with DOI and a DOI-less arXiv-style one (via the real arXiv normalizer), differing in one factor (\cref{fig:dedup}). With a shared DOI every variant merges all pairs (recall 1.00, not plotted). Without one, \code{deduplicate()} and \textsc{uf-repo} merge only identical and case-changed records: a one-year shift, any first-author format change (``A.\ Surname'', ``Surname A''), a trailing period, a changed subtitle separator, a dropped subtitle, diacritic folding and reversed author order each give recall 0.00. The relaxed prototype restores 1.00 except for reversed authors and dropped subtitles.

\subsection{RQ3: local cost and scaling [S]}
\textbf{Normalization and parsing.} Normalizers cost 3.1--6.6\,\textmu s per record; parsing 100-entry arXiv (79\,kB) and PubMed (122\,kB) responses took 2.4--3.8 and 5.7--7.4\,ms (ranges over two executions; providers varied up to 45\,\% between runs, e.g., OpenAlex 6.6 vs.\ 3.6\,\textmu s, so we make no ranking claim). Orchestrating four JSON providers took about 5\,ms at $k{=}10$, 19\,ms at $k{=}100$ and 32--43\,ms at $k{=}200$ ($n{=}15$), linear in the 40--800 candidates and negligible next to 15--30\,s timeouts.

\subsection{RQ4: AI-analysis client [S]}
\textbf{Scheduling.} With $\tau{=}2$\,s, six papers took 10.2, 11.0, 12.0 and 18.0\,s for model latencies of 0.2, 1, 2 and 3\,s, exactly as $5\max(L,\tau)+L$ predicts (\cref{fig:ai}a); median start-to-start gaps were 2\,002, 2\,001, 2\,003 and 3\,004\,ms. Throughput is bounded by $\max(L,\tau)$ per paper.

\textbf{Retries.} Success after one, two or three consecutive 429s took 2.2--2.3, 6.2--6.7 and 14.4--14.8\,s ($n{=}3$), matching $\sum(2^a+0.25)$\,s; four 429s produced four requests in 14.7--14.9\,s and an error (\cref{fig:ai}b). HTTP 400, 401, 500 and 503 were not retried, and \code{Retry-After} is ignored. A failure at paper 3 of 5 was isolated (4 succeeded).

\textbf{Prompt construction.} The user message is \code{Paper Title: \${title}\textbackslash nAbstract: \${abstract}\textbackslash n\textbackslash nTask: \${prompt}} without null handling: a \code{null} abstract (possible for arXiv, PubMed, Crossref) is sent as ``\code{Abstract: null}'', an absent one as ``\code{Abstract: undefined}'', and a 20\,000-word abstract is sent whole (100\,060 characters).

\section{Discussion}
\label{sec:disc}

\textbf{Answers.} \emph{RQ1:} latency is the maximum of adapter times, but that maximum includes adapter-internal serialization (PubMed spacing, Europe~PMC enrichment, arXiv throttle) and has no deadline; failure containment is correct for five providers and misreported for arXiv. \emph{RQ2:} only DOI-sharing records merge reliably; DOI-less records merge only on identical strings, and the outcome depends on input order. \emph{RQ3:} local compute is negligible, but the library view rescans the whole table and scales with rows~$\times$~files. \emph{RQ4:} the client is $\tau$-spaced and serial with bounded 429-only back-off, and sends \code{null} for missing abstracts. The live session contradicted none of these. Quantitative comparison would need per-provider and per-AI-call timestamps, which \RIE{} does not record.

\textbf{Recommendations.} (1)~Make the arXiv adapter reject on errors like the others. (2)~Add a global deadline with partial results (hedging~\cite{dean2013tail} would overload rate-limited APIs). (3)~Configure a Semantic Scholar key, as the code advises. (4)~Use union-find over all records' keys (same cost, \cref{fig:scaling}) with a DOI veto and empty-field guards. (5)~Relax keys only after labelled evaluation on real data. (6)~Bound the Europe~PMC enrichment fan-out. (7)~Guard null and over-long abstracts, honour \code{Retry-After}, retry transient 5xx. (8)~Batch inserts and index the library scan for large libraries. (9)~Call arXiv over HTTPS [C]. None was implemented or evaluated.

\section{Limitations and Threats to Validity}
\label{sec:limits}

\textbf{Emulation and one live session.} In [S] experiments provider latency, rate limits, errors, payload quirks and overlap are emulated; agreement with \cref{eq:tsearch,eq:adapters} shows the code behaves as modelled, not how long real searches take. The only live evidence is one unreproduced session with the gaps listed in \cref{sec:live}.
\textbf{Reconstructed payloads and synthetic corpus.} Payloads are reconstructed, not recorded, so real duplicate rates may differ. Single-factor results (\cref{fig:dedup}) are deterministic properties of the keys, but \cref{tab:e2d} depends on the assumed skew and author format. Unique titles make strict-key false-merge rates lower bounds. No relevance, recall or ranking quality is evaluated.
\textbf{Prototypes and environment.} \textsc{uf-repo} and \textsc{uf-relaxed} exist only in the harness. One 4-vCPU machine and loopback PostgreSQL were used; the GUI, editor, Pandoc export, real PDF downloads (whose \code{fetch} has no timeout or size limit) and the security posture (plaintext keys, broad IPC surface) were only read from code.

\section{Conclusion}
\label{sec:concl}

Running \RIE's unmodified modules against an emulated upstream and a real PostgreSQL server characterized its latency structure (slowest adapter plus throttles, no global deadline), its misreporting of arXiv failures, its order-dependent and DOI-reliant deduplication (fixable by union-find at equal cost), its small local costs, and its serial AI client that sends \code{null} for missing abstracts; a single live Windows session was consistent with these findings. Real latency distributions, overlap rates, retrieval effectiveness and LLM-output quality remain open.

\section*{Reproducibility and availability}
\code{paper\_exp/} holds the sources, figures, harness (\code{run\_all.sh} reproduces every [S] result in about 25 minutes), raw results, logs and verification reports. No application file was modified (baseline \code{bf2d3a3}). Requirements: Node.js~$\ge$18, \code{npm ci --omit=dev --ignore-scripts}, and a local PostgreSQL database \code{rie\_bench}.
